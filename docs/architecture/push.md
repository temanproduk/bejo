# Push notifications (FCM)

> Moved out of `CLAUDE.md` unchanged to keep that file small — it is loaded into every session.
> `CLAUDE.md` keeps the rules and gotchas; this is the detail behind them.

The data-only push design, the producer/queue/consumer split and stale-token cleanup.

## Push notifications (FCM)

**Credentials (`FirebaseConfig`):** an explicit key (`FIREBASE_CREDENTIALS_BASE64` / `_PATH`) wins; otherwise, when `FIREBASE_PROJECT_ID` is set, the app sends as its own service account via application-default credentials — no key file, which is what Cloud Run uses because the org forbids creating service-account keys (that account needs `roles/firebasecloudmessaging.admin`, granted by `init-gcp.sh`). With neither, push is disabled with a warning. A token belongs to one Firebase project: the app's `google-services.json` and the server's project must match, or FCM answers `SENDER_ID_MISMATCH` (which the stale-token cleanup treats as a dead token).

FCM sending lives in `PushNotificationService` (shared). **Every message is data-only** — no FCM `notification` block anywhere, so the app always gets `onMessageReceived` and renders the push itself; `data.type` (`PushType`) says which kind it is.

Transaction push copy renders the amount through `shared/util/Rupiah.format` — Indonesian currency (`Rp 1.000.000`, `.` grouping, `,` for decimals, decimals only when non-zero, never padded to `,00`). It goes in `data.body` only; **no `notification` block is ever added** (see `PushJobSender.buildMessage`, which only calls `putAllData`), since that would stop `onMessageReceived` firing on a backgrounded app and the payment would not be announced aloud. `transactions.amount` is a `BIGINT` of whole rupiah, so the decimal branch is currently unreachable but is implemented + tested.

**Push payloads are polymorphic** (`notification/` module; each module's own payload lives in its `push/` package): every send takes a `PushPayload` — never a raw map — so each kind owns both its data shape and whether it needs high-priority delivery, and adding a push type is a new class, not another hand-built map at a call site. `PushPayload.toData()` yields the wire map; `PushPayload.urgent()` picks the priority. Implementations: `TransactionPushPayload` + `PresencePushPayload` + `AdsPushPayload` (all urgent → Android HIGH, so the app wakes at once and runs its announcement even backgrounded), `SimplePushPayload` (the ad-hoc test-notification payload). Because priority comes from the payload, the fan-out methods are just addressing: `sendToToken` (one device, propagates errors — `POST /api/notifications/test`), `sendToUser` (all a user's sessions — `POST /api/notifications/user`, presence), `sendToDevice` (one `(username, deviceId)` session — the ads flow), `sendToBusiness` (every device of every active user in a business), and `sendToUsernames` (a computed recipient set — the payment callback, keyed by QRIS terminal). The fan-out methods are best-effort and never throw. `NotificationService` (the `/api/notifications/*` endpoints) only sends a push; it does not persist a transaction.

**Delivery queue (`notification/` module) — producer / queue / consumer, swappable for Redis/Kafka later:** the fan-out (producer) resolves *which devices* to notify on the request/callback thread (fast DB reads), then enqueues a **`PushJob`** per device — plain serializable data (`token`, `data` map, `urgent`, `sessionId`, …), **not a closure** — via the **`PushDeliveryQueue`** interface. The **actual FCM send** (the slow network call) runs later on the consumer, **`PushJobSender.deliver(job)`**. The only implementation today is **`InMemoryPushDeliveryQueue`** (a bounded worker pool, `app.push.queue.threads`/`capacity`, default 4 / 1000); because jobs are data and the seam is an interface, a Redis/Kafka implementation drops in by publishing the job + a consumer that calls the same `PushJobSender`. Fan-out methods return the number **queued** (not delivered). Back-pressure is `CallerRunsPolicy` — a full queue runs the send on the caller rather than dropping it; the in-memory queue loses anything still queued at restart (best-effort). Stale-token cleanup runs on the consumer via `SessionStaleTokenHandler` (core's adapter of the `StaleTokenHandler` port, a separate `@Transactional` bean so the proxy applies) with a **race-safe conditional update** (`clearPushTokenIfMatches` — only nulls the token if it's still the one FCM rejected, so a concurrent re-login isn't clobbered). `PushNotificationService.sendToToken` (test endpoint) still sends synchronously via `PushJobSender.sendSync`.

**Stale-token auto-cleanup:** when FCM returns `UNREGISTERED` ("Requested entity was not found" — app uninstalled / token rotated) or `SENDER_ID_MISMATCH`, the dead token is cleared from its `sessions` row so it isn't retried. The classifier is `PushNotificationService.isTokenUnregistered(MessagingErrorCode)`; both the fan-out methods (per failing session) and `NotificationService` (the test endpoint, then rethrows) apply it. Transient/payload errors (`UNAVAILABLE`, `INVALID_ARGUMENT`, …) never delete the token.
